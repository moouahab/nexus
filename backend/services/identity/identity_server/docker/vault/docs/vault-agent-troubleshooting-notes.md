# Vault Agent Troubleshooting Notes

This document records the issues encountered while wiring Vault Agent into the
Docker stack and how they were fixed.

## Goal

The target architecture is:

```text
Vault dev server
  stores runtime secrets

Vault Agent
  authenticates with AppRole
  reads secret/data/nexus/identity
  renders secret files

Postgres, Redis, API
  read rendered secret files
```

The Compose files intentionally avoid `environment:` sections. Runtime values are
passed through commands, config files, Docker secrets, or rendered files.

## Issue 1. Vault Server Is Not Vault Agent

At first it was easy to confuse the two pieces:

- Vault server stores secrets and handles authentication.
- Vault Agent is only a client process. It needs a Vault server to connect to.

For local development, a `vault` service was added:

```yaml
vault:
  image: hashicorp/vault:1.17
```

For production, this local dev Vault service should not be used. Production
should point Vault Agent to a real external Vault instance.

## Issue 2. Avoiding `environment:`

Vault dev examples often use:

```yaml
environment:
  VAULT_DEV_ROOT_TOKEN_ID: root
  VAULT_DEV_LISTEN_ADDRESS: 0.0.0.0:8200
```

This project avoids `environment:` sections, so those values were moved to:

- `secrets/vault_dev_root_token`
- `docker/vault/dev-listen-address`

The final Vault command reads both files:

```sh
vault server -dev \
  -dev-root-token-id="$(cat /run/secrets/vault_dev_root_token)" \
  -dev-listen-address="$(cat /vault/config/dev-listen-address)"
```

## Issue 3. AppRole Files Must Be Generated

Vault Agent needs:

- `secrets/vault_role_id`
- `secrets/vault_secret_id`

These files are not invented manually. They are generated by Vault after:

1. creating the policy,
2. enabling AppRole,
3. creating the `identity` AppRole.

The reproducible procedure is documented in:

```text
docker/vault/docs/generate-approle-secrets.md
```

## Issue 4. Vault CLI `-address` Position

The initial procedure used:

```bash
vault -address=http://127.0.0.1:8200 login ...
```

With the tested Vault CLI, this fails with:

```text
Invalid flags before the subcommand.
```

The fix is to put `-address` after the subcommand:

```bash
vault login -address=http://127.0.0.1:8200 ...
vault kv put -address=http://127.0.0.1:8200 ...
vault policy write -address=http://127.0.0.1:8200 ...
vault auth enable -address=http://127.0.0.1:8200 ...
vault write -address=http://127.0.0.1:8200 ...
vault read -address=http://127.0.0.1:8200 ...
```

This keeps the commands explicit without relying on `VAULT_ADDR`.

## Issue 5. Vault Agent Volume Permissions

Vault Agent initially failed with:

```text
error creating file sink: error during write check:
error opening temp file in dir /vault/token for writing: permission denied
```

Root cause:

- The `hashicorp/vault` image entrypoint eventually runs Vault as the `vault`
  user.
- Named Docker volumes mounted at `/vault/token` and `/vault/secrets` were not
  writable by that user.
- Setting `user: "0:0"` alone was not the right final fix. It still left
  permission preparation in the Compose runtime path.

The final fix is a dedicated Vault Agent image:

```yaml
vault_agent:
  build:
    context: ../vault-agent
```

The image prepares the required directories at build time:

```dockerfile
USER root

RUN mkdir -p /vault/token /vault/secrets /vault/templates \
  && chown -R vault:vault /vault/token /vault/secrets /vault/templates

USER vault

ENTRYPOINT ["vault"]
CMD ["agent", "-config=/vault/config/agent.hcl"]
```

After this, Vault Agent runs as the `vault` user and can write:

- `/vault/token/agent-token`
- `/vault/secrets/postgres_password`
- `/vault/secrets/redis_password`

## Issue 6. `depends_on` Should Wait For Vault Agent Health

Compose `depends_on` with `service_started` only means the container process has
started. It does not mean Vault Agent already rendered secret files.

The stack now gives `vault_agent` a healthcheck that verifies:

- `/vault/token/agent-token`
- `/vault/secrets/postgres_password`
- `/vault/secrets/redis_password`

Postgres, Redis, and API depend on:

```yaml
vault_agent:
  condition: service_healthy
```

The entrypoints still wait for files as a second line of defense before starting
the real process.

Examples:

```text
/run/vault/secrets/postgres_password
/run/vault/secrets/redis_password
```

This makes startup deterministic even when Vault Agent takes a few seconds to
authenticate and render templates.

## Issue 7. Redis Healthcheck Had To Match Vault Files

Redis now reads its password from:

```text
/run/vault/secrets/redis_password
```

The healthcheck also had to use the same file:

```yaml
healthcheck:
  test: ["CMD-SHELL", "redis-cli -a \"$$(cat /run/vault/secrets/redis_password)\" ping | grep -q PONG"]
```

Otherwise Redis could start correctly while the healthcheck still checked the old
Docker secret path.

## Issue 8. Existing Volumes Can Hide Password Changes

Postgres stores its initialized password in its data volume. If the Vault
password changes after the database has already been initialized, the container
may start with a password that no longer matches the API config.

For a fresh local test, ensure the data volume is new or intentionally reset.

Do not delete volumes casually in shared environments. In local development, a
reset is acceptable only when the data can be lost.

## Final Verified State

The full stack was tested with:

```bash
docker compose up --build --detach
```

Verified result:

- `vault` running
- `vault_agent` running
- `vault_agent` healthy
- `postgres` healthy
- `redis` healthy
- `api` healthy
- Vault Agent rendered:
  - `/vault/secrets/postgres_password`
  - `/vault/secrets/redis_password`
  - `/vault/secrets/serverpod-passwords.yaml` in production
- Serverpod started and applied the migration

The most useful validation commands were:

```bash
docker compose ps --all
docker compose logs --no-color --tail=120 vault_agent postgres redis api
docker compose exec vault_agent ls -l /vault/secrets
docker compose config
```
