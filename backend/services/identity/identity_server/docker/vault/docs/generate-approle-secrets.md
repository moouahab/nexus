# Generate Vault AppRole Secrets

This document explains how to initialize the local development Vault setup for
the Identity service.

The recommended path is the script:

```bash
cd identity_server
./docker/script/setup_vault_approle.sh
```

The script is idempotent for local development:

- existing files in `secrets/` are kept;
- missing local secret files are generated;
- Vault policy and AppRole are created or updated;
- `vault_role_id` and `vault_secret_id` are regenerated from Vault;
- Docker Compose is started;
- Vault Agent rendered files are checked.

Do not commit the real `secrets/` directory.

## Script Structure

The entrypoint is intentionally small:

```text
docker/script/setup_vault_approle.sh
```

It loads focused helper files:

```text
backend/infrastructure/service-runtime/script/lib/common.sh
backend/infrastructure/service-runtime/script/lib/docker.sh
docker/script/lib/paths.sh
docker/script/lib/secrets.sh
docker/script/lib/vault.sh
```

Responsibilities:

- `common.sh`: logging, errors, command checks, random secret generation
- `paths.sh`: service root, secret paths, Vault defaults
- `secrets.sh`: local `secrets/` creation and required secret files
- `docker.sh`: Docker Compose startup and Vault Agent verification
- `vault.sh`: Vault login, KV write, policy, AppRole, credential generation

## Required Local Files

The script creates or reuses:

```text
secrets/vault_dev_root_token
secrets/postgres_password
secrets/redis_password
secrets/service_secret
secrets/email_secret_hash_pepper
secrets/jwt_hmac_sha512_private_key
secrets/jwt_refresh_token_hash_pepper
secrets/vault_role_id
secrets/vault_secret_id
```

`vault_role_id` and `vault_secret_id` are not invented manually. They are
generated by Vault after the policy and AppRole are configured.

## Vault Secret Path

Vault Agent reads the Identity runtime secret from:

```text
secret/data/nexus/identity
```

The script writes these keys:

```text
postgres_password
redis_password
service_secret
email_secret_hash_pepper
jwt_hmac_sha512_private_key
jwt_refresh_token_hash_pepper
```

These keys are used by the Vault Agent templates to render:

```text
/vault/secrets/postgres_password
/vault/secrets/redis_password
/vault/secrets/serverpod-passwords.yaml
```

## Optional Environment Variables

You can override the local defaults:

```bash
VAULT_DEV_ROOT_TOKEN='my-local-token' ./docker/script/setup_vault_approle.sh
VAULT_ADDRESS='http://127.0.0.1:8200' ./docker/script/setup_vault_approle.sh
VAULT_POLICY='identity-read' ./docker/script/setup_vault_approle.sh
VAULT_ROLE='identity' ./docker/script/setup_vault_approle.sh
VAULT_SECRET_PATH='secret/nexus/identity' ./docker/script/setup_vault_approle.sh
```

Defaults are defined in `docker/script/lib/paths.sh`.

## Manual Equivalent

The script performs the equivalent of these steps:

1. create `secrets/` from `secrets_example/` if needed;
2. generate missing local runtime secrets;
3. start the local Vault service;
4. login with `secrets/vault_dev_root_token`;
5. write Identity runtime secrets to Vault;
6. create/update the `identity-read` policy;
7. enable AppRole if it is not already enabled;
8. create/update the `identity` AppRole;
9. generate `secrets/vault_role_id`;
10. generate `secrets/vault_secret_id`;
11. start the full Docker stack;
12. verify Vault Agent rendered files.

## Verification

After the script succeeds, check:

```bash
docker compose exec vault_agent ls -l /vault/secrets
```

Expected rendered files:

```text
postgres_password
redis_password
serverpod-passwords.yaml
```

The API does not need a host-mounted `config/passwords.yaml` in Docker. It uses
the Vault Agent rendered Serverpod password file.

## Local Only

This script is for local development and reproducible developer environments.
Production must inject AppRole credentials through the deployment platform
secret store.
